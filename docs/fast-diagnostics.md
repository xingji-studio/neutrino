# 极速模式调试记录

本轮目标是找出变慢的具体机制。新增离线诊断脚本与结果记录，没有修改 Standard 或 Fast 的运行算法，没有调用付费模型，也没有改写之前的性能结果。

诊断对象为交付构建 `2261361cf8276f9b047e7fbd8fd00f7ab450c16ffe9334a608901767f2a365fc`。脚本为 `scripts/diagnose-fast-mode.mjs`，完整结果、任务区间和请求事件在 `docs/fast-diagnostics.json`。

## 真实数据重新核对

只比较双方都通过验收的七类样本，排除后续余额不足中断的样本：

| 指标 | Standard | Fast |
| --- | ---: | ---: |
| 墙钟时间 | 590.54 秒 | 1041.75 秒 |
| 剔除人工审批等待后的诊断时间 | 503.96 秒 | 996.45 秒 |
| 输入 Token | 720,955 | 1,616,266 |
| 输出 Token | 70,116 | 160,215 |
| 模型请求 | 204 | 252 |
| 工具调用 | 107 | 137 |
| 工具累计执行时间 | 3.35 秒 | 6.55 秒 |

剔除人工审批等待后，Fast 仍慢约 97.7%。因此，人工审批等待不能解释这组结果的退化。七类成功 Fast 样本均没有重规划或调度器重试；不能把它们的变慢归因于反复重试。

Fast 的真实模型请求分组为：规划 7 次、工作 Worker 67 次、`verification` 162 次、最终整合 16 次。其中 `verification` 包含自动审批，并不都是独立正确性验证。该合并栏共 860,053 Token，约占 Fast 总量的 48.4%；旧数据缺少进一步拆分所需的记录。

工具累计时间不等于墙钟时间，可重叠；上表不能用于精确反推模型纯推理时间。历史数据没有逐请求时间线、实际并发度和各类资源等待时间，无法追溯每个机制究竟贡献了多少秒。

旧 `scheduling_ms` 也不覆盖全部快照、持久化和 Web 回调成本。新夹具单独记录了 checkpoint 次数与累计耗时，但它们使用临时目录、脚本模型和小型产物，不能替代真实会话的持久化开销测量。

## 已复现的问题

离线夹具使用真实的 `FastAgentEngine`、调度器、文件工具、Shell 工具和原有 `ApprovalGate`，模型回复由脚本提供。所有方案保留对三份输入或输出的实际独立检查与最终审查。网络被禁止，供应商 Token 与真实模型延迟均未测量。

| 夹具 | 工作节点 | 脚本模型往返 | 独立检查工具调用 | 额外审批模型调用 | 同时活动的工作任务峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 合并读取三份资料 | 1 | 6 | 3 | 0 | 1 |
| 分开读取三份资料 | 3 | 14 | 3 | 0 | 3 |
| 分开读取，输入需自动审批 | 3 | 26 | 3 | 12 | 3 |
| 三个独立 Shell 检查任务 | 3 | 14 | 3 | 0 | 1 |
| 三个不相交目录的编辑任务 | 3 | 14 | 3 | 0 | 3 |

这些是结构性调用次数和实际资源占用的复现，不是模型速度对照。脚本中的 5 毫秒延迟只用于观察交错顺序，不代表供应商推理耗时。

### 1. 拆分自动放大验证与模型往返

`src/fast/scheduler.ts:59` 在每次新增工作节点时，自动新增一个 `.verify` 节点。工作与验证都各自运行完整模型循环。

读取三份相同资料的两种夹具，实际都执行六次读取：执行者读三次，独立验证者再读三次；最后都进行全局审查。但其调用结构不同：

```text
一个工作节点：Planner 1 + 工作 2 + 验证 2 + 最终审查 1 = 6 次
三个工作节点：Planner 1 + 工作 6 + 验证 6 + 最终审查 1 = 14 次
```

Planner 提示词虽然要求简单任务只用一个 Worker，但没有基于模型往返成本的拆分准入判断。`estimated_duration` 当前用于排序，不会阻止负收益的拆分。历史真实计划还包含 `final_verify`、`independent_verify` 这样的工作节点，它们也被再次验证，最后仍需全局审查。

已证明的是拆分产生的固定调用放大；不能据此断言真实任务的全部局部验证都多余。应按验收标准确定验证覆盖，再消除重叠职责。

### 2. Worker 输入中重复包含主提示词

调用链为：

```text
WebSession.buildApiMessages 先把主提示词写入 history[0].content
FastAgentEngine.worker 再直接附加 options.system
随后把包含 history[0] 的完整 history 序列化附加到同一 Worker 系统消息
```

对应 `src/web/session.ts:933` 和 `src/fast/engine.ts:235`。每个夹具首个 Worker 都检测到主提示词两份：一份原文，一份位于序列化历史中；它们会随该私有对话的多轮请求重复发送。

这证明输入装配存在重复。重复角色指令是否进一步引起模型重复规划或检查，旧记录不足以证明，不能直接当成已测事实。

### 3. 独占范围覆盖整个 Worker，而非单条命令

`src/fast/scheduler.ts:259` 根据正在运行的任务判断冲突。任务从启动到模型与工具循环全部结束，都保留其访问范围，包含模型思考、等待工具审批和生成报告的时间。

三个无依赖的只读任务可以同时活动；三个无依赖的 Shell 任务虽然有四个模型槽位，同时活动的工作任务仍只有一个。夹具 Shell 命令本身无需自动审批，排除了审批队列导致串行的因素。

该策略有避免任意命令破坏工作区一致性的必要理由。问题在于，Planner 把“需要命令”直接映射为整段任务全局独占，限制了可实现的并发收益。不能通过直接删除冲突检查来修复。

### 4. 局部编辑的验证被升级为全局独占

`src/fast/scheduler.ts:62` 使用 `exclusive: !task.read_only`。即使源任务只允许写入独立目录，验证者也会获得全局独占范围，以便执行可能需要的测试。

在三个不相交目录的夹具中，真实调度顺序为：

```text
A 编辑结束
→ A.verify 因 B/C 的编辑仍在运行而等待
→ B/C 编辑结束
→ A.verify、B.verify、C.verify 依次执行
```

这里没有 A 到 B/C 的业务依赖，验证也只需读取各自目录里的文件。等待来自默认扩大后的访问范围。它形成了业务 DAG 中看不到的资源依赖，并延长了验证和后继任务的关键路径。

应显式描述验证所需读写范围、命令和隔离条件，不能只根据“源任务能否写入”决定验证范围。

### 5. 自动审批整段串行，并被统计为正确性验证

`src/fast/engine.ts:351` 把自动审批模型绑定为 `verification`；下一行又让所有需要审批的调用通过容量为一的 `approvalPool`。

原审批策略规定每次自动审批有两个独立模型评估。在读取夹具中，六次需审批的读取产生十二次审批模型请求，总模型往返由 14 增至 26。自动审批决策的并发峰值为一，即使模型槽位仍有空余。

同一夹具里真正独立验证的模型往返是六次，原 `verification.requests` 却显示十八次，正好包括十二次审批请求。这解释了旧指标为什么不能直接用于归因。

Standard 同样使用原审批策略，不能把全部审批成本算成 Fast 独有。Fast 多出的工具调用可能放大这项成本；历史数据没有记录具体审批调用数，无法精确量化。后续优化应区分人工审批界面的串行需求与自动评估的并发能力，保留原评估人数、权限规则和判定标准。

### 6. 本地缓存命中没有减少 Worker 的输入装配

`src/fast/artifacts.ts:21` 的 `readContext` 只是返回完整文本并增加命中计数。调度器的输入版本检查也会调用它，所以命中数不能解释为节省了多少模型读取或 Token。

三工作节点的夹具加入 20,000 字符历史后，累计请求 JSON 体积从约 277 KB 增至约 558 KB；本地命中数仍为 66。长历史继续进入每个 Worker、验证者和后续轮次。

这些是请求对象的字节计数，不是供应商 tokenizer 或缓存计费数据。供应商可能存在自动缓存，但旧接口没有提供可靠的命中与费用记录，其效果仍未知。

## 调整优先级

1. 先分离自动审批、局部验证、执行、上下文压缩和最终审查的指标。记录模型排队、获得槽位、首个输出、结束时间，以及工作区和审批的等待原因。
2. 删除输入装配中的重复系统提示词，保留全部原始用户约束、相关上下文、审批规则和可追溯历史。
3. 建立任务拆分的成本判断，按验收覆盖组织验证；避免对已有隐式验证的节点再创建重复审查任务。
4. 给验证者明确的访问范围与检查清单；对于命令并发，使用可验证的隔离，保留一致性保障。
5. 分别设计人工审批呈现与自动评估调度，维持相同的安全审查标准。

这些是后续修改顺序，并不表示已经修复或达到 50% 提速。全局审查、必要局部检查、原模型和推理档位仍必须保留。

## 复现与检查边界

```sh
node scripts/diagnose-fast-mode.mjs
```

需要已编译的 `dist`，以及允许 Node 启动本地子进程的执行环境；沙箱若禁止子进程，Shell 夹具无法通过。脚本只使用临时文件和脚本模型，不读取用户模型凭据，退出时恢复环境并删除临时夹具。

七组夹具通过断言，包括每组三次真实独立检查、缓存与请求体积、模型角色计数核对、独占范围阻塞关系和运行结束后的取消监听清理。并发期间出现 Node 默认监听数量警告，但结束后根信号的监听器为零；本次未发现监听累积泄漏。

核心引擎构建指纹与此前 77 个测试文件通过时一致。本轮没有重跑付费对照，也未把脚本请求数、估算 Token 或毫秒定时器结果当成真实模型性能提升。真实样本的 P95、逐请求耗时归因与大规模任务表现仍未验证。
