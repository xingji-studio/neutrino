# Agent 静默停止：证据、复现与治理方案

调查日期：2026-11-24。下文事件时间使用 Asia/Shanghai（UTC+08:00）；原始 journal 使用 UTC。

范围：排查截图中的 Neutrino 会话，并按用户后续“按规划修复”的授权实现修复。截图里的 ar.io 部署请求是故障证据，不是本次要执行的任务。故障注入使用隔离数据目录、受控模型和独立测试进程；没有重启、暂停或向正在运行的真实会话发送消息，没有切换全局安装或真实后台服务。

## 结论与证据边界

已证明的系统性问题是：**任务执行所有权依赖 UI 进程/页面，执行连接与任务结果混为一谈，失去 live 注册会被当成完成；恢复后的验收又没有稳定绑定原任务。** 这使多种中断具有相同的“说到一半就结束”外观，也使局部补丁无法覆盖整类故障。

**尚不能证明这一次执行者为何变得不可用。** 当前持久化资料缺少执行者 PID/进程实例、退出原因、阶段心跳和失联事件，因此不能在终端进程退出、桥接不可达、注销注册等路径中确定唯一触发点。没有 crash.log 也不等于进程未被外部结束。以下复现证明代码缺陷存在，不等于证明用户操作过这些入口；用户明确反馈没有任何操作。

不能诚实保证机器永不关机、进程永不被杀或外部模型永不故障。可以通过实现与测试约束系统：中断不得冒充成功；任务身份和目标不得随 UI 消失；恢复必须有所有权与副作用检查；每次可观测的停止必须可归因，硬杀而缺失的原因明确标成未知。

## 四个可重复的缺陷

运行：

```powershell
npm run build
node scripts/diagnose-silent-stop.mjs
```

复现器使用隔离的临时 HOME、真实编译后的类及从 `web/app.js` 提取的实际函数，禁用外部网络。它是现状诊断，不是“修复测试通过”；输出 `reproduced: true` 表示缺陷仍然存在。

1. **页面生命周期吞掉执行者的可见身份。** `src/screens/chat.ts:360` 的 `onDeactivate()` 明知任务可继续运行，仍无条件 `hub.unregister()`。再次 `onActivate()` 又因 `initialized` 提前返回。实测 `busy === true`，退出及再次激活后均没有注册。这个入口不证明用户本次退出过页面。
2. **短暂传输故障被升级成删除会话。** `src/web/terminalBridge.ts:193` 每次轮询最多等待 1500ms；第 213 行起，连续四次异常直接关闭全部镜像并清空映射。实测执行者仍 busy，第四次失败后旧 live key 消失，恢复后产生新 key。四次失败不是固定总时长，实际取决于每次请求耗时及轮询间隔。
3. **没有 live 连接被视作任务完成。** `web/app.js:1353` 的 live 状态只看 busy 等标志，`sessionStatus()` 对无 liveKey 的历史直接返回 `done`；第 1662 行加载历史时固定 `active:false`。实测保存状态为 `partial`，侧栏仍返回 `done`，末轮被折叠，最后一句进度说明成为可见的“答复”，待执行工具被藏入折叠区。`listSessions()` 也没有把任务状态传给侧栏。
4. **续做保留了历史文字，却丢了正式验收目标。** `src/screens/chat.ts:949`、`src/web/session.ts:698` 都用最新审批 prompt 初始化 `TaskRuntime.request`；`StandardTask` 仅据此建立 requirement inventory。复现器调用真实终端 `runTurn()`，只替换模型工作为观测器：原目标仍在 `priorUserRequests`，正式 requirements 却只剩“开始？”。这是验收目标被削弱，不是说模型完全看不到历史。

前三项组成了截图外观的可解释路径：执行者不可用 → live 注册消失 → 选择切回历史 → 历史被当成 done → 未完工具被折叠 → 只剩进度说明。第四项让续做也不能可靠地继承原来的验收责任。

- `node scripts/test-terminal-lifecycle.mjs`
- `node scripts/test-web-recovery.mjs`
- `node scripts/test-web-sidebar-status.mjs`

其中 `scripts/test-web-sidebar-status.mjs:147-151` 明确把“保存的历史按定义就是 done”写成注释和正确断言。因此仅要求旧测试全绿不足以验收此问题。增加提示词、放宽完成门禁或无限自动发送“继续”也不能恢复已失去的执行者，还会增加重复副作用及费用。

## 推荐的整体方案

以**一个后台任务控制器、持久化任务状态、独立执行尝试、UI 仅作客户端**替换终端/网页分别拥有主循环的模式。复用现有 TaskRuntime、Standard 验收、命令归属和审批逻辑，不重写这些领域规则；迁移的是所有权与生命周期。

### 1. 单一任务所有权

- 后台服务是任务记录的唯一状态写入者；terminal/web 通过相同协议提交、观察、暂停、恢复任务，不再由 `ChatScreen` 或 `WebSession` 的页面生命周期拥有执行。
- 每个任务使用持久化 `taskId`；每次运行用独立 `attemptId`；连接 key 只是订阅句柄。刷新、切页面、桥接中断均不改变前两者。
- 执行进程持有包含进程实例 UUID、PID、启动时间、generation 的 lease。PID 复用和超时心跳不能单独作为可启动第二个写入者的依据。
- 后台服务也需要用户级进程监督和重启后的恢复扫描。仅把代码移进一个常驻进程，不能抵御该进程自身退出。

### 2. 持久化状态机，分开任务、尝试与连接

建议使用事务存储（例如 SQLite；落地时需验证项目支持的 Node/Windows 打包环境），保留现有会话 JSON 作为兼容导出。任务、执行尝试、工具意图、审批、证据和事件采用可迁移 schema；状态更新与事件追加在同一事务中提交。

- 连接状态：`connected / reconnecting / disconnected`，从不决定任务完成。
- 任务状态：`queued / running / waiting_user / interrupted / reconciling / blocked / completed / failed / cancelled`，由控制器按合法迁移写入。
- 执行尝试保存 owner、阶段、开始/结束时间、最后进展、退出码或信号、停止原因、前序 attempt。强制结束且原因不可知时保存 `owner_lost_unknown`，不得伪造退出原因。
- 服务启动扫描所有没有有效执行者的运行记录，先进入 `interrupted/reconciling`；UI 直接显示已保存状态，最后未完轮次展开。历史缺失终态就是“状态未知/需恢复”，不是默认 done。
- 兼容当前版本期间，先纠正 hub 注销和桥接删除语义：保留稳定身份，显示连接断开；确认 owner 丢失时记录中断。不要把保留快照伪装成仍有执行者。

### 3. 可靠恢复，但不盲目重放工具

每个工具调用使用稳定 callId，在执行副作用前持久化意图、参数指纹及审批绑定。建议阶段为 `prepared → awaiting_approval → approved → executing → succeeded/failed/unknown`；结果和 evidence 持久化后才允许推进任务。

恢复时先确认旧执行者和它拥有的命令已停止，或明确接管其可验证句柄；租约过期本身不够。只有确认不存在并发写入者后才能启动新 attempt。generation fencing 用来拒绝旧 worker 的新操作，但不能撤回已经发出的 shell 或 HTTP 副作用。

“执行已发生，结果还没落盘”无法对任意 shell/外部系统提供通用 exactly-once。只读操作可安全重试；写文件可检查预期 hash/原子替换状态；外部操作需幂等键或结果核对。无法判断的操作标为 `unknown` 并进入 reconcile/明确阻塞，不能直接再执行一次。审批过期或参数改变时重新走门禁，恢复不得扩大授权。

### 4. 原任务与当前输入分开保存

持久化 `TaskSpec`：原始目标、约束、需求清单、目标修订号、验收证据映射。短促的“继续/开始？”关联未完成 taskId，创建新 attempt，不重新定义验收目标。

仍单独保留最新用户消息供审批使用。历史目标是上下文，不是永久授权；后续取消、收窄范围、切换任务要显式改变 TaskSpec/任务关联，不能靠把所有历史拼接到审批 prompt 来解决。

### 5. 阶段监督与唯一完成出口

- 模型、审批、工具、清理各自有开始/进展/结束事件、相应超时策略与取消传播。记录 provider 请求标识（可获取时）、owner、阶段及停止原因，避免下一次只剩两条 `model_started`。
- 区分等待长工具和模型流已无进展。为连接、流空闲、审批分别设置可配置超时；重试要有次数与预算边界。重试耗尽进入可见的 blocked/failed，不假装完成，也不无限消耗令牌。
- `completed` 只能由控制器在当前 TaskSpec 的所有要求通过适用的验收、没有 pending/unknown 工具、没有剩余授权工作时提交。模型自然 stop、文本宣称完成、流 EOF、页面 idle、失去连接都不是完成事件。
- 明确用户暂停、等待审批、预算耗尽、真实阻塞等合法停止；目标是消除无归因的静默终止，不是无条件让 agent 永远运行。

## 改造顺序与发布验收

建议按依赖交付三批，不能把第一批独立宣称为彻底修复：

1. 持久化真实状态、失联/退出归因、历史展示与目标继承；修正 hub/bridge 的注销语义，并把本文四个诊断案例改为健康状态回归断言。
2. 引入后台 TaskController 和任务存储，逐个把 terminal/web 驱动迁入同一执行入口；保留旧历史可读。已有会话不得为热更新而强制终止；新旧 worker 必须有明确版本与归属。
3. 加上恢复协调、工具意图日志、进程监督与故障注入发布门禁；验证候选构建后，在无活动任务窗口切换全局安装及后台进程，确认实际运行构建标识。

验收必须在 Windows 实际运行，并覆盖控制器、工具执行者、网页三方，而非只测假 DOM：

| 故障注入/情景 | 必须观察到的结果 |
| --- | --- |
| 切终端页面、关闭浏览器、断 SSE | 执行持续，taskId 不变；连接变化不改变任务终态 |
| 桥接连续失败超过四次后恢复 | 同一任务身份恢复；断开期间明确显示失联 |
| worker 被结束/父终端退出 | 中断及 owner 丢失可见；由监督器按策略恢复，不显示 completed |
| 后台服务退出/重启、重复恢复请求、系统休眠 | 持久化任务可扫描；owner 核对后最多一个有效写入者；无法核对则阻塞 |
| 审批卡住、流 EOF/截断、模型断网 | 阶段超时/错误可归因；按预算重试或明确阻塞 |
| 工具在发送前、执行中、成功后但记结果前崩溃 | 意图/结果状态正确；未知副作用先核对，不盲目重复执行 |
| “开始？/继续”及后续取消、收窄范围 | 保留完整验收目标；最新授权限制仍然生效 |
| 保存了 running/partial/blocked 的会话重开 | 清楚显示未完成，最后未完轮次和工具上下文可见 |
| 模型只给进度说明、漏需求、检查失效 | 无法提交 completed；仍有可执行工作时继续处理 |

发布判据是这些不变量在确定性故障注入与真实进程集成中成立。它们能给出可审核的工程保障；不能把有限测试写成“任何未来故障绝不发生”的保证。

## 本轮完成情况

- 四项原始缺陷已转为健康状态断言：`node scripts/diagnose-silent-stop.mjs --assert-healthy` 的复现数为 0/4，外部请求为 0。
- 生产终端、网页和独立本地 API 的新任务统一使用私有后台任务服务，执行引擎复用 headless `WebSession`，界面只订阅和提交操作。终端离开页面会释放订阅，不会释放任务执行权。网页直接发现后台任务，不依赖原终端桥接保持可见。
- `src/tasks/controller.ts` 实现 taskId / attemptId / owner / leaseId、跨进程单写入者锁和执行前所有权核对。存储采用带版本和校验链的 fsync 事务 WAL，将状态和事件一起提交；保留现有 JSON 导出，没有引入 SQLite 原生依赖。尾部半条事务可恢复，中间校验损坏、所有权不确定或持久化失败均阻止进一步执行。
- `src/tasks/worker.ts` 将监督器与执行器分离，记录退出码/信号并进行有次数边界的退避重启。反复崩溃耗尽额度后记录 blocked，客户端不能通过反复连接清空额度。服务采用独立发现文件和仅回环、Bearer 鉴权的 API，不覆盖公共 `api.json`，不开放额外网页端口。构建指纹不匹配时拒绝自动替换已有执行者。
- 恢复先检查旧 owner 和 WAL。模型阶段及已结束的安全操作可恢复原 taskId 和完整目标；未确认结果的命令、写入等副作用进入 `tool_outcome_unknown`，不会重放。受控工具在执行前保存稳定 evidenceId/意图，以同一 ID 记录结果，不靠“参数相同”猜是哪次调用成功。崩溃前尚未消费的队列输入保留并明确要求核对。
- 接受回执随用户消息持久化；回包丢失后以同一 request_id 核对，不重复追加或执行；同一 ID 换消息内容会拒绝。上一轮执行权释放前，不启动下一轮；暂停后的新 attempt 也须等待旧执行者清理完成。
- 模型响应体默认 180 秒无数据超时、600 秒无内容进展超时（心跳不能无限掩盖停滞），分别通过 `NEUTRINO_STREAM_IDLE_TIMEOUT_MS` / `NEUTRINO_STREAM_PROGRESS_TIMEOUT_MS` 配置；不限制长工具的总运行时间。HTTP 错误正文也受超时保护，仅保留前 500 个字符，不会因服务仅返回错误响应头而无限等待。无输出时沿用有界重试，已有输出则保留部分结果并明确失败。OpenAI 兼容流必须有 `[DONE]` 或 finish_reason，Anthropic 流必须有 message_stop（保留兼容网关的 `[DONE]`）；缺失终止标志的 EOF 不产生可执行工具或成功结果。模型、审批、工具事件及停止原因进入 WAL。
- 历史与实时 UI 分别处理执行状态和连接状态；未完成任务不再当 done，最后未完轮次保持展开。审批转发绑定 approvalId，旧审批不能批准新调用。
