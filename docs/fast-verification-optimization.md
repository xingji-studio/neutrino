# 验证层级优化

本轮针对详细诊断中出现的 `实现 → 局部验证 → 验证工作 → 再次局部验证` 串行链，合并验收职责并支持直接执行的独立检查。模型、推理档位、输出预算、审批规则和最终全局审查保持原配置。

## 验收职责

| 检查内容 | 所属节点 | 独立性与通过条件 |
| --- | --- | --- |
| 实现、研究、编写或修复测试代码 | `kind: work`，省略 kind 也按此处理 | 工作节点之后仍自动生成 `.verify` |
| 单个工作产物的必要来源、正确性、边界条件及测试 | 在发布工作节点前写入其完整 `acceptance_criteria` 和 `output_contract` | 自动验证器使用独立会话执行完整标准；开发自检不能代替独立检查 |
| 多个已验证产物之间新增的集成检查，或用户明确要求的额外独立复核 | `kind: verification`，依赖所有相关产物 | 直接以验证角色执行一次；要求明确的 `verification_passed: true` 且 `unresolved: []`；不再生成第二层 `.verify` |
| 全局约束、冲突、缺失覆盖和最终回答 | 最终主智能体全局审查 | 必须引用所有当前有效的规划产物，包括显式验证节点的产物 |

规划器在发布任务前合并重叠的本地检查，不依赖名称猜测或删除已有节点。名称包含 `verify` 的普通工作节点仍得到独立验证器。创建测试文件和修复实现仍属于工作任务；验证节点发现错误后应报告失败并请求显式修复。

单个工作任务可以直接包含“实现模块并通过这些独立测试”的验收标准。对于分别实现的两个模块，只有新增的跨模块行为才需要额外的显式验证节点：

```text
module_a → module_a.verify ─┐
                           ├→ integration_check → 全局审查
module_b → module_b.verify ─┘
```

`integration_check` 的 `kind` 为 `verification`，没有 `integration_check.verify`。普通工作及其验证器、显式检查都受原有资源池、审批、超时、取消、工作区访问和共享预算约束。需要 Shell 的检查仍使用独占访问。

后继节点同时收到依赖的验收标准、对应版本的独立验证产物和实际工具证据，便于判断哪些检查已经覆盖。只有依赖产物及其对应版本的验证产物都已通过，才会提供这份独立验收覆盖；开发自检不会被算作独立验收。该清单不能替代当前节点自身的必要检查。

## 失败与恢复

- 显式检查等待全部依赖的当前版本完成独立验证后才能启动；版本不匹配时阻塞。
- 否定结论、缺少布尔结论或未解决项都不能解锁后继。
- 上游失效会传播到显式检查及其后继；已经运行的旧代结果不会被发布为成功。
- 执行过可能产生副作用的检查不能自动重放。显式修复完成后，原检查保留原输入依赖并增加修复产物，重新执行自身验收，不能直接用修复任务的结论替代。
- 最终审查遗漏显式检查产物、引用旧版本或在仍有失败节点时宣称完成，都会被拒绝。
- Web 进度统计和产物整合包含显式检查，同时避免重复计算自动 `.verify` 节点。

## 验证方法与证据边界

新增 `scripts/test-fast-verification.mjs`，使用脚本化模型回复驱动真实引擎，并在临时目录中通过实际文件工具和 Node 命令检查算术模块；不调用供应商模型。

| 同一受控任务的规划方式 | 逻辑模型往返 | 必要独立检查 | 最终全局审查 |
| --- | ---: | --- | --- |
| 原先的实现任务 + 验证工作任务，两者各带验证器 | 11 | 实际执行并通过 | 保留 |
| 将本地检查合并到实现任务验收标准 | 7 | 完整标准由独立验证器实际执行并通过 | 保留 |
| 保留额外检查，标记为显式验证节点 | 9 | 额外检查直接独立执行一次 | 保留 |

这些数字包含规划、工具返回后的后续轮次及最终审查，只证明受控规划减少了重复模型往返。回复和 usage 为脚本生成，不用于声称真实模型提速、Token 节省比例或质量提升。合并方案还注入真实的加法实现错误，确认保留的独立测试能够检出错误并阻止完成。

回归同时覆盖多前驱、负面或缺失判定、输入版本、动态失效、显式修复、取消、任务数量上限、最终引用和真实进度卡。`npm test` 全量 81 个测试脚本通过，覆盖 Fast、Standard、审批、权限、插件和会话等功能。随后补强修复时的原依赖保留与独立验收证据传递，重新构建并通过 `npm run test:fast` 的全部 6 个脚本；本轮顺序、源码指纹和结果见 `fast-verification-test-results.json`。

以上为优化开发阶段的验证。后续已按相同模型、Max 档位和外部验收标准，重新完成一次多模块编码场景的 Standard / 优化后 Fast 真实配对：49.32 秒 / 110.60 秒，已报告 Token 为 98,532 / 131,102，功能质量检查均通过。Fast 有一次 HTTP 500 尝试没有 usage；本轮不能提供完整 Token 账单。完整结果及原始证据见 `docs/fast-optimized-live-comparison.md`。稳定速度分布与一般质量评测仍未完成，上一轮预算中止样本不作为本轮配对成绩。
