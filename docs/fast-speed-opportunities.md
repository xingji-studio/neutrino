# Fast Mode：下一轮速度优化依据

后续批处理与主审指令优化已落地，新增真实对照、验收和最新累计预算见 [Fast Mode 模型往返优化](fast-roundtrip-optimization.md)。下文保留优化前的离线诊断依据。

数据来自 [V3 原始测试](fast-efficiency-v3-benchmark.json) 的全部 12 个成功 Fast 样本。其中复杂 DAG 为 `parallel_analysis` 的三轮。模型仍为 DeepSeek/deepseek-flash、Max、4 个模型槽位；各项原始验收要求不变。本报告不新增或重算 Standard/Fast 提速结论，原有失败及审批中止样本仍完整保留在原始报告中。

模型池等待的**累计值**仅 0.69、0.74、1.06 秒；它不是可直接节省的墙钟时间。复杂 DAG 的持久化累计中位数约 61 毫秒，扣除嵌套 run 持久化后的同步快照与存储合计中位数约 81 毫秒。增加并发槽位或重做存储不会消除这条串行链，优先级低于减少链上的模型往返。

## 2. 优先试：在每个角色内部合并执行和验收步骤

保留协调器独立重算、后续独立验证以及最终主审，合并**同一角色**内可一次完成的步骤。建议协调器的一条完整 Node 命令依次执行：

1. 读取全部原始文件，检查记录完整性及字段要求。
2. 独立重算数值，与实际检查员报告逐项核对；出现分歧时明确失败。
3. 写入结果，重新读取已保存文件，断言结构、每项数值和总数符合要求。
4. 输出可引用的实际检查结果，供独立验证节点审查。

这会尝试减少“读文件一轮、计算一轮、落盘一轮、自验一轮”的拆分。独立验证节点使用自己的检查方法；不能把协调器的同一份脚本作为独立验证的替代。

三轮串行尾段中，审批模型请求区间取并集后为 **10.11、9.50、17.19 秒**。这些时间已包含在上表中，不能再次相加。合并一个完整且相关的命令体，可以尝试减少工具和审批往返；每个实际命令仍走原有风险判定、普通审批票数和极端风险审批轮次。审批必须检查完整命令体，不能把多个动作包装后隐藏风险。失败检查应抛出错误或明确返回失败，不能只打印 `false` 后继续宣告通过。

现有日志中的额外检查不能一概删掉：第三轮检查员报告出现辅助字段错误，最终主审又写错一次加权汇总表达式，后续检查分别识别并解决了这些问题，详见 [质量观察记录](fast-efficiency-v3-quality-observations.json)。这说明必须保留处理矛盾和修正错误的检查能力。

| 轮次 | 只列目录的开场模型回合 | 这些回合报告的 Token | 模型请求累计时间 | 模型请求区间并集 |
| --- | ---: | ---: | ---: | ---: |

| 2 | 2 | 8,353 | 1.98 秒 | 1.71 秒 |
| 3 | 3 | 12,773 | 5.26 秒 | 2.68 秒 |

共 7 个回合、29,390 Token。统计按同一只读 scope 的首个模型回复仅包含成功 `list_files`、下一回复成功读取任务已知源文件识别；已在同一回复中列目录和读文件的情况不计入。

可在 Fast 只读任务策略中明确：路径已由任务给定时，直接读取所需源文件；确有列目录需要时，把列目录与已知路径读取放在同一回复。只读工具和路径限制保持不变，缺失路径及读取失败仍由模型处理。

这些是**已发生回合的消耗**，不是预测收益。改动会影响后续消息和模型选择，并且几路请求并行；不能把累计时间当作整次任务可节省的时间，也不能假定全部 29,390 Token 都会消失。

## 4. 上下文策略应同时考虑漏装和重复装载

`src/fast/engine.ts` 的最终主审系统消息来自通用主 Agent 策略，后者要求运行命令验证；Fast 特有的“复用当前已验证证据，针对缺口、冲突或变更补查”规则在用户消息中。这是一个**需要 A/B 确认的潜在诱因**，现有数据不能证明提示层级导致了重复验证。

建议在主审的系统策略中明确角色职责：完整审查原始需求、当前版本的验收覆盖、跨任务一致性与全部独立检查；遇到缺失、冲突、输入变更或必要的集成检查时使用完整工具能力补查。依然必须完成最终全局审查，不能提前接受未验证任务，也不能取消原始要求中的命令测试。

另一个实际开销来自必要报告未在当前节点内联：第一、三轮的协调器独立验证分别通过 `read_task_evidence` 补读四份原始检查员报告，响应为 7,205、9,666 UTF-8 字节。第二轮也补读了原始读取记录。这些调用有明确的核对依据，不能标为无用查询。可以试验根据当前节点验收要求预装**授权依赖链内**所需的报告，完整保留版本、结论、假设和异常；用增加的输入量与减少的一次往返做实测权衡。不能恢复无边界地附带所有历史产物。

输入缓存命中 Token 占输入 Token 的比例中位数已约 **70.3%**，缓存命中仍计入报告的输入 Token。上下文去重仍可能减少传输和推理负担，但不能把已有缓存描述成尚未启用的优化，也不能据此推算费用。

## 5. 次优先：原始需求的无损引用原型

单任务模式已在运行时系统指令完整呈现原始需求，同时任务目标和验收条目又各有一份相同文本。离线原型仅把这两处完全相同的字段换成原始需求引用，完整需求仍保留在运行时指令及实际任务记录中。对 9 个单任务样本逐字展开后与原片段完全一致。

| 场景 | 原目标与验收片段 | 引用片段 | 片段差额 |
| --- | ---: | ---: | ---: |
| 多源检索 | 893 字节 | 109 字节 | 784 字节 |
| 多模块代码 | 1,033 字节 | 109 字节 | 924 字节 |
| 强顺序依赖 | 1,261 字节 | 109 字节 | 1,152 字节 |

这只是重建字段片段的 UTF-8 字节比较，未计入引用解释指令、其他提示字段、分词和缓存行为，不是 provider 请求或 Token 降幅。完全相同的内容可以复用引用，语义相近、空白不同的验收条目不得误删；模型是否可靠理解引用还需单独验证。该规模低于复杂 DAG 的串行往返开销，安排在前述优化之后。

## 6. 验证方式与实现顺序

先单独调整“已知路径读取批处理”，观察 7 个开场回合是否减少；再调整同一角色内部的命令批处理及主审职责；最后评估依赖报告预装和需求字段引用。逐项实验便于判断收益来自哪里，避免同时变更多个机制后无法归因。

本次仅运行离线分析与校验：

```sh
node scripts/test-fast-opportunities.mjs
node scripts/analyze-fast-opportunities.mjs
```

测试覆盖并行区间并集、阶段截断、scope 匹配、已批处理调用排除、重试 Token 汇总、缺失 usage 不记作零、需求文本逐字保留、日志丢失和 usage 矛盾拒绝，以及捕获路径迁移；禁用网络后复现全部 12 个 Fast 样本。机器可读结果见 [fast-speed-opportunities.json](fast-speed-opportunities.json)。脚本没有重放工具、调用模型或更改生产策略，因此没有新增端到端提速结论。

后续真实 A/B 继续固定模型、Max、输出 allowance、所有原始验收要求和独立检查，记录同一场景的墙钟、全部实际 Token、审批/工具回合、缓存和失败样本。已授权累计 1,050 万 Token，上一轮保守统计已用 9,681,397，余额 **818,603**；本次分析未消耗该额度，完整 24 次新对照不能默认沿用成新的无限预算。
